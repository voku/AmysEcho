## Agent Task Brief
Goal: the app asks for persistent storage where the browser offers it and shows the result; a corrupt or partly written profile is detected at start and reported with a restore path instead of crashing or showing an empty board; multi-step writes are atomic; the caregiver area shows when the last backup was exported. Scope: src/profiles/, test/, docs/storage.md. Depends on: NG-2, NG-19. Issue 1176 slice S5. From the NG-2 reviews: an unknown storage schema makes the store refuse to open and leaves a family with no export path; a layout change needs a migration or a read-only export for old layouts before it ships, and a stale cached app after an update fails the same way. Two tabs or an installed app plus a tab are not coordinated (data.set racing remove can leave an orphan key); use Web Locks or a transactional read. From the NG-25 reviews: a profile that got over the export limits (possible only through two uncoordinated tabs) can be exported with raised limits, but that document can only be imported into a store opened with the same raised limits and no part of the app does that; provide a restore path for such a backup. Provide a salvage export for profiles listed as damaged (unreadable name, unbuildable stored value) so intact data is never trapped. Restoring a near-limit backup peaked at about 400 MB of memory in Node because the data is copied three times; measure on a low-memory phone and reduce copies. exportProfile can surface ProfileSizeError instead of ExportSizeError for an unbuildable stored value. Comments in store.ts (open) and backup.ts (ImportOptions.limits) still describe limits as only lowered; align them. From the NG-12 reviews: a backup is not self-contained, because board entries for catalogue concepts carry only an id (or an override); restoring under a later app version with a changed catalogue changes or drops concepts. Follow the catalogue decision on NG-13. From the NG-28 reviews: boards imported from an older backup have no stored wording and follow the live catalogue until their concepts are next set through setBoardConcepts; a hand-edited backup can add the copied marker to a caregiver's wording, which then gets refreshed on re-choosing, so validate board entries on import; removeCustomConcept cannot reach ids that board data cannot address. From the NG-29 reviews: the caregiver area has no backup control and no navigator.storage.persist() request; the notice at the name field says so and must change together with this card (rule 9 in docs/caregiver.md).
