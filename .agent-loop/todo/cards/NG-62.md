# NG-62: Backup: make sure the file really reaches the new device (follow-ups of NG-58)

- **Ticket:** NG-62
- **Lane:** BACKLOG
- **Domain:** product
- **Created:** 2026-11-25T20:47:20+00:00
- **Updated:** 2026-11-25T20:47:20+00:00
- **Summary:** From the NG-58 reviews. The backup works in Chromium, but the real purpose, moving to a new device, depends on steps the app cannot see: whether the download happened, how the file travels, and the password on the new device.
- **Next:** 1) The success line 'Die Sicherung ist gespeichert' is shown although the browser may have declined or broken the download (iOS Safari asks first; blob downloads in an installed iOS app are unreliable; the click comes about a second after the tap): say 'Die Datei wurde zum Speichern angeboten' and ask to check it, tell caregivers to restore on the new device before resetting the old one, and offer navigator.share({ files }) where available. 2) Show 'Stand der Sicherung: <date>' (exportedAt, available after decrypting) in the conflict question, so 'Ersetzen' with an older file is a choice made knowingly. 3) autocomplete='new-password' lets a password manager generate a password the caregiver never sees, missing on a device of another platform: add a hint to write the password down. 4) Near the 64 MB limit saving and restoring hold several copies in memory (about 0.5 GB): measure on a low-end phone; consider binary clips or streaming. 5) Mobile file pickers may grey out '.amysecho' (accept list): try on iOS and Android. 6) Docs for caregivers: how the file gets to the new device and that the app needs one online first visit there. 7) Smaller: a copy restore keeps the display name (two profiles of one name); a failed save after leaving its view shows its line elsewhere; typed passwords and the chosen file are cleared after an error; the outer header is not bound as AES-GCM additional data (not exploitable).
- **Validation:** npm ci --ignore-scripts && npm run verify
